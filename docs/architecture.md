## ADR-1 · RAG 走"本地 ChromaDB + 分块 + CrossEncoder 精排"，并用 2×2 消融定配置

**状态**：已落地（阶段 4 改造、阶段 6 定口径）

**背景**
知识库要当**语义记忆**用（记录使用过程中积累的经验/习惯），不是企业文档问答。所以要求是：
离线可用、不联网、不能让"检索"变成黑盒。改造前是**整篇文档直接入向量库、不做精排**。

**决策**
1. 分块入库（collection `terminal_knowledge_v2`，id = `source#块序号`，元数据带 `source` 便于增量替换）；
2. 召回后加一层 **CrossEncoder 精排**（模型从本地路径加载，**路径不存在就降级为纯向量召回、不联网**）；
3. 用 **2×2 消融 + 全量召回对照组**决定"要不要分块、要不要精排"，而不是拍脑袋：
   `A 整篇+无精排`（改造前）/ `B 整篇+精排` / `C 分块+无精排` / **`D 分块+精排`（生产）** /
   `E 分块+精排+全量召回`（上限参照）。这套对照**不用 LLM、不烧 token**，所以随时可复跑。

**后果（含代价）**
- 收益：文件粒度 top-1 **0.6 → 0.9**、真源 top-1 0.4 → 0.6、干扰源命中 0.6 → 0.4；
- **代价：平均延迟 12.8ms → 86.7ms（约 6.8 倍）** —— 精排买的是准确率，不是速度；
- E 组（把 35 个块全塞给模型）是 1.0/0.7/0.3 ⇒ **检索有损，但损失不大**（这条对照让"要不要精排"有了上限参照）。

**备选与否决理由**
- 换云端 embedding/rerank：违背"离线可用、不联网"，且会引入 API 成本与超时面；
- 混合检索（BM25 + 向量）/ 查询改写：**收益未验证**，而当前语料只有 35 条原子，先不做（避免"为指标好看"扩语料）。

**证据**：`docs/evidence/rag_ablation_20260923_203822.json`（旧语料）、
`rag_ablation_20260924_053228.json`（语料修订后，**报告采用这份**）、
`docs/evidence/评估报告.md` 第七节。

## ADR-2 · 评测体系：通过 = 满分、skip ≠ 0、超时也验分；并且**不设人为闸门**

**状态**：已落地（阶段 6 重建）

**背景**
旧评估体系被删掉，因为它的尺子是坏的：`score >= 0.5` 记通过（部分分能把通过率抬起来）、
环境不可用记 0 分（把"没测"算成"做错"）、超时题直接 0 分（哪怕产物已经写出来了）；
更糟的是安全题的判定器**对着不存在的工具名空转**，恒定满分。

**决策**
1. **通过 = 满分**；部分分单列 `partial` 并在报告里披露占比；
2. **`skip` ≠ 0 分**：环境不可用记 `ok=None`，全部 skip 的题标 `unavailable` 且**不进分母**；
3. **超时/异常也跑判定器**；
4. 判定器按**真实 MCP 工具名 + 真实参数名**写，`assert_known_tools()` 对着 `permissions.ALL_TOOLS` 校验
   （改题集有机械守卫：每题至少 1 条状态断言、8 个维度各 ≥3、对抗题不许真打危险命令）；
5. 四档强度：文本 10 / 轨迹 29 / **状态 124** / LLM 评分 0 —— **分主要靠状态断言**（真实产物：文件 / 库表 / WSL / 接口）。

**后果（含代价）**
- multi 轮出现过一次**人为闸门制造假失败**：E015 被 `TASK_TOKEN_BUDGET=200k` 掐断、烧掉 257k 仍判失败；
  改成"只计量、不拦截"后**同一轮 30/30 且总成本更低**（1.64M vs 1.78M token）⇒ 从此生产口径只计量。
- 代价：`skip` 不进分母意味着"环境不好时分数会更好看"，所以报告必须同时披露 **skip 数**与
  "全部 skip 的题不计入"这条规则（否则就成了新的自欺）。

**备选与否决理由**
- 每题多跑几次取平均：**成本 ×N**，且当前题集对模型已饱和（两轮都满分），方差信息有限 ⇒ 记进"后续规划"而不是现在做；
- 引入 LLM 评分档参与通过判定：判定器里留了 `TIER_JUDGE`，但**本批题集一题没用**（评分模型自身不稳，会污染判定）。

**证据**：`docs/evidence/v3-single.json` / `v3-multi.json`（正式两轮）、
`v3-multi-limit200k.json`（限额版对照，**留着就是给这条教训作证**）、`docs/evidence/评估报告.md`。

## ADR-3 · 上下文工程：结果外置 + 白名单豁免 + 历史压实 + 双层 token 预算

**状态**：已落地（阶段 4）

**背景**
Agent 的上下文会被"读大文件 / 长命令输出"迅速烧掉。但**粗暴外置**会适得其反 —— 这是实测出来的：

**决策**
1. 工具结果超阈值（6000 字符或 150 行）→ 落盘 `runtime/tool_results/`，上下文只留预览 + 路径；
2. **`read_file` / `read_file_range` 在豁免名单里，绝不外置**（见下）；
3. 读 `tool_results/` 里的文件**不再外置**（同内容同 hash ⇒ 会指向同一个文件 = 死循环）；
4. 历史估算超 `COMPACT_THRESHOLD` → 最老一段压成四段式摘要，**摘要失败就原样保留**（省 token 不能把历史弄丢）；
5. token 预算分两层：`NODE_TOKEN_BUDGET` 剪枝 + `TASK_TOKEN_BUDGET` 硬终止，
   且任务级要在 **executor 的 ReAct 循环内部逐步判**。

**后果（含代价）**
- 反例的价值大于正例：同一道"读全文并总结"的题，**外置后模型看不见内容、改用分段读绕过去 ⇒
  12 次工具调用 / 25 步，token 从 17,361 涨到 127,071（7.3 倍）** ⇒ 才有第 2 条豁免名单；
- 只在节点入口判预算会漏：一次"读大文件 + 反复重读"能在**单个节点调用**里烧十几万 token ⇒ 才有第 5 条的"逐步判"；
- 代价：粒度是"每步一判"，所以实际可能在"上限 + 一步成本"处才停（实测设 12000 时在 26,456 停下并报告）；
- 代价：外置让"结果在哪"变成两跳（预览 → 文件），排查时要多看一眼路径。

**备选与否决理由**：直接截断长结果（会丢信息，模型会重读/瞎猜）；把摘要交给小模型（多一次调用 + 引入新失败面）。

**证据**：`tests/test_context.py`（外置规则、豁免、压实、预算都打桩测过）。

## ADR-4 · 用 LangGraph 三阶段 + MCP 工具层，并把"工具包装"做成唯一入口

**状态**：已落地（阶段 1–5）

**背景**
要"多 Agent 协作"又要"工具能真干活"，两者都容易做成黑盒：一个把编排藏在 prompt 里，一个把工具调用散在各处。

**决策**
1. 编排用 LangGraph `StateGraph`：`route_node`（复杂度路由）→ Planner / Executor / Verifier；
   Verifier 只拿**只读白名单**工具（12 个），打回上限 `MAX_RETRY=2`；
2. 工具全部走 **MCP stdio 子进程**（6 个自建 server，32 个工具）+ FileManagementToolkit（7 个文件工具）；
3. **所有工具调用统一过一次包装**（`utils/tool_wrap.py`）：**权限判定 → 结果外置 → 只读缓存**，
   顺序不能换、且 CLI / Web / 评估**三条入口都要接**（漏一条，那条入口就既不做外置也不走缓存）；
4. 执行过程通过 `agent/events.py` 推**节点级进度**（ContextVar sink，没绑就静默跳过），Web 端复用现有 WebSocket。

**后果（含代价）**
- 好处：权限/外置/缓存是**一处实现、三处生效**，且能被单元测试钉住（"判定必须在缓存之前"有测试守着）；
- **代价：MCP 每次调用自建并自关一个 stdio 会话** ⇒ RAG server 因为要 import 原生扩展，
  每次调用要付 **≈8 秒**子进程启动（换来的是"不在事件循环里加载原生扩展"，避免死锁，见 ADR-5）；
- 代价：MCP 工具的接口形状是 `StructuredTool(coroutine=…)`（**没有 `func`**），
  而 FileManagementToolkit 的工具**只有同步 `_run`** ⇒ 包装层必须分别处理两条路径。

**备选与否决理由**
- 不用 MCP、全做成进程内工具：启动快，但失去"工具是独立进程、可单独探针调试"的性质，
  且与本项目"演示 MCP 编排"的目标不符；
- 用 `MultiServerMCPClient` 当上下文管理器复用连接：**它的 `__aexit__` 是普通函数，调用即抛
  `NotImplementedError`**（实测），所谓"复用"不存在。

**证据**：`tests/test_tool_wrap.py` / `tests/test_mcp_tool_lifecycle.py` / `tests/test_integration_mcp.py`（真集成）。

## ADR-5 · 权限与安全：三档档位表 + 判定在缓存之前；**WSL2 只是隔离执行环境**

**状态**：已落地（阶段 5）

**背景**
这个 Agent 会执行 shell、读写主机文件。要么给一层能解释清楚的闸门，要么就别声称"安全"。

**决策**
1. 32 个工具列**三档档位表**（只读 14 / 写执行 18 / 高危 6），默认「需确认」；
2. 判定入口 `permissions.enforce()` 放在工具包装的**第一句**（缓存查询之前）；
3. Web 端弹框（含参数 JSON、倒计时、"本会话总是允许"）+ CLI 阻塞询问 + **超时自动拒绝** + `runtime/permissions.log` 审计；
4. **对外措辞**：只说「WSL2 隔离执行环境（命令黑名单 + 应用层三档权限）」，**不说"安全沙箱"**。

**后果（含代价）**
- 明说的边界：**WSL2 默认把 Windows 盘挂在 `/mnt/c`**，而 `vm.py` 还在主动用这条通道 ⇒ 它**不是安全边界**；
  也没有"Agent 只能在工作区内操作"这个保证（README 里如实写了）；
- 命令黑名单被修过一次**形同虚设**的漏口：`\brm\s+-rf\s+/\s` 要求 `/` 后面还得有空白字符 ⇒
  最经典的 `rm -rf /`（结尾即 `/`）**直接放行**；现在改成"flag 用后瞻匹配、顺序无关"，并覆盖 `rm`/`del`/`rd`/`ri` 别名；
- 代价：「需确认」档下写操作都会停下等人（评估里用 `AutoApprover` 但**逐条留痕**，
  这样成绩才能证明机制真的在跑：两轮实测 **24/30 与 23/30** 道题经过闸门）。

**备选与否决理由**：只靠命令黑名单（正则永远补不全）；把 WSL 当沙箱（不成立，且会误导使用者）。

**证据**：`tests/test_permissions.py`（32 工具一个不多一个不少 + 四条实现约束）、
`tests/test_dangerous_commands.py`（打桩 subprocess，断言危险命令走不到启动子进程那一步）。

## ADR-6 · 会话存储分家：`checkpoints.db`（引擎）+ `sessions.db`（我们自己的元数据）

**状态**：已落地（阶段 7）

**背景**
Web 端要"历史会话列表 + 标题 + 置顶 + 回收站"。而 `runtime/checkpoints.db` 是 **LangGraph
`AsyncSqliteSaver` 的地盘**（它按 `thread_id` 存图状态），我们不该往里塞业务字段。

**决策**
1. 侧车库 `runtime/sessions.db`（`app/web/sessions.py`）：`thread_id / title / title_source /
   created_at / updated_at / deleted_at / pinned`；
2. 列表由**两张表拼**：checkpoint 表提供"时间与条数"，侧车提供"标题 / 置顶 / 是否删除"；
3. **删除永远先软删除**（`deleted_at` → 回收站），只有回收站里再点「彻底删除」才真删
   `writes → checkpoints`（顺序不能反：`writes` 引用 `checkpoint`）；
4. 标题取"新会话的第一条用户消息"，**用户改过就不再被自动覆盖**（`title_source='user'`）；
5. "这个会话正在被使用"用 **`_active_threads` 计数**判断，**不用 `_session_locks`**。

**后果（含代价）**
- 代价：多一个文件、多一层"两张表要对齐"的逻辑（比如侧车有行而 checkpoint 已被清）；
- 收获：引擎的东西不被污染；删会话能做得**可撤销**（软删除 + 回收站），而 LangGraph 的原生 API 没有这个概念；
- 🔴 **一条踩出来的教训**：`_session_locks` 按设计**不回收**（连接断了空 Lock 还留着），
  拿它当"会话是否活着"的判据 ⇒ **早已断开的会话永远删不掉**。所以另起计数表，
  在 WS 建立 / `new_session` / `load_session` / 消息带 `threadId` / 断开 五处维护，
  对活会话一律 `409`（前端先自动新开一条再删）。

**备选与否决理由**
- 把元数据塞进 `checkpoints.db`：两边抢同一把 sqlite 锁，排查时分不清谁写的；
- 用文件名/目录存会话（一个会话一个文件）：与 LangGraph 的 checkpoint 机制重复，且丢了事务性。

**证据**：`tests/test_web_sessions.py`（25 条，侧车库）、`tests/test_web_sessions_api.py`（9 条，含"活会话不许删"）。

## 附：这些决策"错了吗"——三条自查

1. **有没有靠人为闸门制造好成绩？** 没有；反而修掉了它（ADR-2 的 200k 闸门案例，同一轮改口径后**成本更低**）。
2. **有没有为了指标好看去改口径/扩语料？** 没有；RAG 语料 35 条原子，改了干扰项后**指标变差**也照实归档两份。
3. **有没有把该说清的代价写下来？** 有：精排 6.8 倍延迟、MCP 每次 ≈8 秒、压实可能留下"上限 + 一步"的尾巴、
   WSL2 不是安全边界 —— 都写在各条 ADR 的"后果"里。
