### 三条设计取舍（刻意这么定，别"优化"回去）

1. **协作式，不做强制取消**：`asyncio.Task.cancel()` 只在 `await` 点生效，掐不断同步阻塞调用（`subprocess` / 文件 IO / `input()`），半路强杀还会让"哪些副作用已经发生"变成未知。
   ⇒ **正在飞的那一次模型调用不会被打断**，但它之后的步骤一定不会再开始（实测见证据 4）。
2. **副作用一律保留，不回滚**：停止只保证"后面不再继续"（回滚自己也可能失败，还会掩盖现场）。
3. **`TaskCancelled` 继承 `BaseException`**（不是 `Exception`）：工具调用发生在 LangGraph 的 `ToolNode` 里，它 `except Exception` 会把异常变成**一条 ToolMessage**交给模型 ⇒ 停止会退化成"模型看到一条奇怪的错误、再决定下一步"（多烧一次调用，还可能换个办法接着干）。
   ⚠️ 代价写进了 `AGENTS.md`：所有可能穿过它的入口都要**显式接住**（各节点 + `run_multi_agent` 兜底 + `_run_chat`），且**不许**把 `_run_chat` 那条写成 `except BaseException`（会吞掉 WS 断开时的 `asyncio.CancelledError`）。

### 顺手挖出来的第三个问题（F3）：终止的那一轮**没被计次**

写 P1 的测试时撞出来的：`retry_count` 只在 Executor **正常跑完**时自增；
被预算或停止掐断的那一轮即使是"被打回后发起的"，也不计数 ⇒ 结果卡片会写「打回 0 次」，
而实际上明明被打回过。
**修法**：把 `is_retry` 提到**所有终止分支之前**算，三条返回路径（正常 / 预算 / 停止）都计一次。

还有一条**同族**的（比 F3 更接近 R5 的真实形状）：第 1 轮跑完 → Verifier 判 FAIL（`verdict` 留在 state 里）
→ 打回重跑 → 第 2 轮撞上预算 ⇒ 那时最终回复会走"验收未通过"那条包装分支，变成
「任务执行完成，但验收未通过（已重试 1 次）：验收意见：… 执行结果：【已终止·预算】…」
—— **正是第 2 题现场那句看不懂的混合文案**。修法：`budget_exceeded` 时**不套**那层包装
（那一轮根本没验收，谈不上"验收未通过"）。

### 🔴 一处**偏离候选池原文**的决定（留痕）

候选池 §十五B 写的是「含 `<…>` / `{…}` / `${…}` / `你的XXX` ⇒ 直接回问」。

另有 `你的XXX` 一种（XXX 里必须含中文占位词），并做了**重叠丢弃** ——
否则 `<你的WSL用户名>` 会同时套出 `你的WSL用户名>/ngin` 这种噪声片段（第一版就是这样）。

## 八、P2 做了什么（预算放宽 + 阈值按模型窗口自动算 · 候选池 §十三①）

**问题**（阶段 7 收尾时就记下了）：三项阈值是**全局写死**的（6000 / 30000 / 200000），跟「当前用哪个模型」无关 ——
换个 32k 窗口的模型，`NODE=30000` 可能**一次调用就撞窗口**；换个 1M 窗口的模型，压实阈值 6000 又过于保守（一直在摘要）。
而 200000 的任务级保险丝在真实长任务里也太紧（探索测试第 2 题烧到 208,509 才被它掐断）。

| # | 改动 | 落在哪 |
|---|---|---|
| 1 | 新 `TokenBudgets` + `budgets_for_window()`（纯函数）+ `token_budgets()`（运行期解析） | `config.py` |
| 2 | 模型可声明 `context_window`：内置注册表 `config/models.json` / 自定义模型（Web 面板） | `model/llm.py` · `web/server.py` · `SettingsPanel.vue` |
| 3 | Executor / 压实判定改成**运行期**取额度（换模型不必重启） | `multi_agent.py` · `context.py` |
| 4 | `.env.example` / `config/models.json` 的 `_readme` 同步说明 | 两处 |

**解析顺序（高→低）**：显式环境变量（老名字不变）> 该角色模型的 `context_window` > `CODE_AGENT_CONTEXT_WINDOW`
（全局覆盖）> 128000。

**比例**：压实 **15%** · 单次调用输入 **35%** · 任务累计 **max(50 万, 4×窗口)**（封顶 200 万）。
128k 窗口 → `19200 / 44800 / 512000`；1M 窗口 → `64000 / 200000 / 2000000`。

### 🔴 一处**又一次偏离候选池原文**（留痕）

候选池 §十三① 写的是 `TASK ≈ 60~70%`（窗口的百分比）。**那比今天还紧**：
128k × 65% ≈ 8.3 万 < 现在的 20 万，与「把预算放宽到 50 万~100 万」的结论**正好相反**。
⇒ 2026-10-07 定：任务级按「**窗口倍数 + 下限**」算（`max(50 万, 4×窗口)`）——
它本来就不是「能不能塞进一次调用」的问题，而是「**愿意为一个任务花多少**」的成本保险丝。
（`tests/test_token_budgets.py::test_task_budget_is_a_cost_fuse_not_a_window_fraction` 把这条钉住了。）

### 证据

- `tests/test_token_budgets.py`（新，**10 条**）：128k 的期望值、窗口越大额度越大且封顶、
  **env 永远优先**、没声明窗口回落 128k、脏值（`128k` 这种字符串 / 负数）不抛、
  🔴 **给自定义模型声明 200k 窗口 ⇒ 额度立刻变成 30000 / 70000 / 800000**（不用重启）。
- 受影响的既有测试改的是**注入方式**（不再 patch 已不被读的模块常量），**断言强度一处没降**：
  `tests/test_context.py`（压实阈值改成显式 `threshold=`）、`tests/test_termination.py`
  （`tiny_task_budget()` patch 解析函数）、`tests/test_cancel.py`（状态条与解析值对齐）。
- 全量：`pytest` **700 passed**（覆盖率 **78%**）· `ruff check` + `ruff format --check` 全过。

### ⚠️ 对**本机现有 `.env`** 的影响（要人做一步）

`.env` 里**显式写死**了 `CODE_AGENT_COMPACT_THRESHOLD=20000` / `CODE_AGENT_NODE_TOKEN_BUDGET=30000`
/ `CODE_AGENT_TASK_TOKEN_BUDGET=200000` ⇒ 按「env 优先」，**这三个值仍然生效**，新的窗口推导**不会**替换它们。
想让「预算放宽 + 按窗口算」真正落地，二选一：
1. 把 `.env` 里这三行**删掉/注释掉** ⇒ 完全按窗口自动算（128k 默认模型 → 19200 / 44800 / 512000）；
2. 或者把 `CODE_AGENT_TASK_TOKEN_BUDGET` 手动改成 `512000`（其余两行可留可删）。

### 没验证到的

- **真机没跑过「换一个声明了窗口的模型 ⇒ 额度跟着变」**（单测覆盖了整条链路：注册表 → config → 事件）。
- **`context_window` 的默认值 128000 是拍的**：模型名与窗口没有可靠的离线映射（不猜），
  所以没声明的模型一律按 128k 算 —— 用 1M 窗口的模型时建议在面板里填一下。
